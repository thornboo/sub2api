# 站内文本工单

反馈以工单形式保存：用户提交问题后，可以查看自己的记录、阅读管理员回复并继续补充信息；用户和管理员都可以结束工单。所有内容仅支持纯文本。

## 使用流程

1. 已登录用户进入“我的反馈”（`/feedback`）；仅持有本站 API Key 的用户在 `/key-usage` 成功查询后进入该 Key 的工单列表。
2. 点击新建并填写问题。提交成功使用站点通用成功提醒，清空输入并关闭新建弹窗。登录页面刷新列表并定位新工单；Key 查询页关闭反馈弹窗，用户再次主动打开记录时定位新工单。
3. 点击工单进入详情，查看最初的问题和双方回复。工单列表与回复均分页，回复标明发送方和时间。
4. 进行中的工单允许用户补充、管理员回复。打开详情或点击刷新时获取最新消息和状态。
5. 任意一方确认关闭后，工单保留可查看的历史，显示关闭方及时间，双方均不能继续发送消息。

状态只有 `open`（进行中）和 `closed`（已关闭）。本轮不提供重新打开、附件、富文本、站外通知或实时聊天连接。

## 未读提醒

- 工单列表在编号旁显示小红点，悬停可查看未读条数。管理端和登录用户、Key 用户都使用相同提示样式，红点与工单是否关闭无关。
- 管理员收到用户新建的问题或补充消息时产生未读；用户收到管理员回复时产生未读。自己一侧发送的内容不算未读。
- 已读进度持久保存在服务端，按工单和查看者身份区分。每位管理员分别记录；登录账号和 Key 身份继续隔离，刷新页面或更换设备不会重置已读记录。
- 只有在可见页面中成功打开详情、加载并展示最新回复页后，才确认到本次实际获取的最新消息编号。列表查询、加载失败、旧分页、隐藏页面和过期请求都不会自动清除未读。
- 已读位置只前进。旧标签页的迟到请求不会退回已读状态，也不会把读取完成后才到达的新消息误标为已读。关闭工单不等于读完消息，已关闭工单仍可查看并消除未读。
- 反馈列表打开且页面可见时，每 15 秒静默检查更新；隐藏标签页、离开页面或退出身份后停止。当前对话处于最新页时可刷新收到的回复，并在成功展示后确认已读；查看历史分页时保留新消息提醒。
- 上线前没有历史阅读记录，因此既有对方消息在首次成功读取前会显示未读。

## 身份与可见范围

- 登录入口使用现有 JWT 鉴权，只能操作当前账号以登录身份发起的工单。
- Key 入口使用现有 HttpOnly 查询 Cookie，只能操作该 Key、原所属账号和成员身份一致的工单。不能看到所属账号的登录工单或其他 Key 的工单。
- 查询资格沿用现有 Key 查询会话规则；禁用、过期或额度耗尽不会单独取消反馈资格。每次请求重新验证查询会话，Key 被删除或归属改变时旧会话失效。
- 列表、详情、回复读取、发送消息和关闭都由后端校验权限。客户端不能通过指定账号、Key、成员或发送方来扩大权限；越权访问与不存在的工单都返回 404。
- 管理员可以查看和处理全站工单。账号邮箱、脱敏 Key 等处理信息仅出现在管理员 DTO；客户回复列表不暴露管理员个人身份或平台内部字段。
- 浏览器切换登录身份或 Key 查询会话时，清除旧工单、草稿和对话状态，取消或忽略仍在进行的请求。

## 文本与频率

- 用户新建工单和补充消息共用连续 60 秒的提交冷却：登录身份为 `user:<user_id>`，持钥身份为 `key:<api_key_id>`。
- 登录账号与每把 Key 分别计时；刷新浏览器或重新查询同一把 Key 不会重置后端限制。
- 管理员回复不占用用户冷却；查看工单和关闭工单也不占用该冷却。
- Key 接口保留按 IP 的入口保护，用于限制无效查询会话请求；入口保护不替代按实际身份计算的提交限制。
- 正文去除首尾空白后必须为 1～2,000 个 Unicode 码点，保留内部换行，不接受 NUL。提交正文只接收严格 JSON，整个请求体最多 32 KiB，不接受附件字段、上传表单或多段 JSON。
- HTML、Markdown 图片语法和 URL 均按文本展示，不加载图片、不生成链接预览、不由服务器抓取。新建和回复正文不写入通用审计请求体。
- 身份、内容、权限和已关闭状态检查应先于冷却占用；实际写入前还会在事务内重新检查工单状态。Redis 无法判定冷却时拒绝客户提交。
- 内容提交占用 Redis 冷却后再写入 PostgreSQL。写入失败或结果未知时保留冷却；失败响应不代表内容已保存，用户可在冷却结束后重试。
- 超限为 HTTP 429，提供 `Retry-After` 和 `metadata.retry_after`。倒计时仅用于界面提示，后端判定为准。

## 关闭与并发

关闭是不可逆的产品操作，界面在关闭前明确说明后果。重复关闭保持成功且不改写首次关闭方和时间。

发送回复与关闭在事务中锁定同一工单行：如果关闭先完成，后续消息写入返回 HTTP 409（`FEEDBACK_CLOSED`）；如果回复先完成，该消息保留，随后工单关闭。双方都受此约束，不能通过旧页面或直接请求继续发送。

客户端遇到已关闭冲突后刷新详情，展示关闭状态并移除发送入口。已经关闭的工单始终可在相同权限范围内查看。

## 接口

所有路径以 `/api/v1` 为前缀，沿用项目标准响应包装。三个工单前缀分别是：

| 前缀 | 权限与范围 |
| --- | --- |
| `/feedback` | 登录用户自己的登录工单 |
| `/key/feedback` | 有效 Key 查询 Cookie 对应的工单 |
| `/admin/feedback` | 管理员，全站工单 |

| 方法与前缀后的路径 | 功能 |
| --- | --- |
| `POST /` | 用户或 Key 新建 `{ "content": "问题描述" }`；管理员前缀不提供新建 |
| `GET /` | 分页列表，可筛选 `status=open` 或 `closed`，按最近活动倒序 |
| `GET /:id` | 工单详情，包含最初正文及关闭信息 |
| `GET /:id/messages` | 分页读取后续消息，最新消息在第一页；最初正文不重复为回复 |
| `POST /:id/messages` | 发送 `{ "content": "补充或回复" }` |
| `POST /:id/close` | 提交 `{}` 关闭工单 |
| `POST /:id/read` | 提交 `{ "last_read_reply_id": 123 }` 确认已展示的最新回复编号；没有后续回复时用 `0` 确认最初问题 |

新建成功返回 HTTP 201，数据包含 `id`、`created_at`、`retry_after`；回复成功返回 HTTP 201，包含 `message` 和 `retry_after`。关闭返回当前工单。旧的任意修改状态 PATCH 接口已移除，不能通过它重新打开工单。

用户工单 DTO 仅包含编号、最初正文、来源、状态、创建及更新时间、关闭方和关闭时间、`unread_count`；消息包含编号、工单编号、`author_role`（`user` 或 `admin`）、正文和发送时间。管理员工单 DTO 另外包含处理所需的账号与脱敏 Key 信息。已读接口校验工单归属及消息编号归属，不接受客户端指定查看者身份，不占用正文提交冷却。

## 存储与验证

`239_create_feedbacks.sql` 保留原始反馈表定义；`240_feedback_tickets.sql` 将 `pending` 转为 `open`、`processed` 转为 `closed`，补充关闭信息及消息表，保留旧反馈正文。历史已处理反馈按管理员关闭迁移，以原更新时间填充关闭时间；这是旧数据转换约定，不是新增的实际关闭事件。新版本沿用应用现有启动迁移流程，不修改已发布迁移内容。

`241_feedback_read_receipts.sql` 新增按工单、查看者类别和查看者编号区分的已读进度表，以及用于查询未读回复的索引。确认已读不会修改工单正文、状态或最近活动时间。

删除 Key 或企业成员时保留工单正文与原提交来源；工单另存不随成员删除清空的原成员编号快照，避免重新分配 Key 后获得旧成员的对话。删除所属用户时工单随账号级联删除，回复随工单删除。已删除 Key 的处理信息显示“Key 已删除”。

验证覆盖应包括：创建成功提醒与弹窗关闭、个人列表和管理员回复可见性、跨账号与跨 Key 拒绝、客户 DTO 无内部信息、双方关闭、重复关闭、关闭与回复并发、关闭后双方发送拒绝、创建与回复共享限流、分页、身份切换和失败草稿保留。

未读验证另外覆盖：新问题提醒管理员、双方只统计对方消息、不同管理员独立已读、查询不自动已读、已读位置只前进、晚到回复仍未读、关闭不清除未读、读取失败和隐藏页面不确认已读、自动检查的暂停与清理。
